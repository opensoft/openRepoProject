## Council-Identified Constraints

### N1. What "supported" means for 3.10 at its upstream end of life
**Raised by:** product-advocate
**Concern:** The README would call 3.10 supported in the month upstream
security support for it ends (PEP 619, October 2026), and the example sentence
says "supported" without saying what the word means for this tool.
**Design impact:** The README's range sentence says that each listed version
is run by CI; no end-of-life wording is added. The floor stays 3.10 (R4
deferred, Decision 5); raising it is Brett Heap's separate decision, with
Ubuntu 22.04's `python3` and `add-project-overview`'s 3.10 constraint as its
inputs.

### N2. (L)'s wording if L2 is chosen
**Raised by:** product-advocate
**Concern:** L1 answers a looped parent with the system's raw `ELOOP` text,
while every other parent obstacle gets a sentence that states the repair
("choose a parent that is a directory").
**Design impact:** Decision 6 stands with L1. The design carries L2's exact
sentence beside L1, `The parent PARENT is a symbolic link loop; choose a
parent that is a directory.`, PARENT as given, ASCII, with the AC2
expectation for each, so a choice of L2 needs no second council.

### N3. `AGENTS.md:19` names the floor only
**Raised by:** product-advocate
**Concern:** `AGENTS.md:19` keeps "Python 3.10+", the open form that C2
rejects for the README.
**Design impact:** `AGENTS.md` is agent-facing and names the floor; the README
is the user-facing range. It stays unedited unless Brett Heap asks; if he
does, a one-line edit to "Python 3.10 to 3.15" is in scope, and AC6 does not
read `AGENTS.md`.

### N5. The archive order is guarded by a task

### N6. One source for the parent
**Raised by:** systems-architect
**Concern:** S1 builds the unresolved PARENT from `args.into or args.parent or
os.environ.get("PROJECTS_DIR") or Path.home() / "projects"`, a copy of
`projects_dirs()`'s choice (`project:77-80`); a later change to one can drift
from the other, and feature 005 reads the same defaults.
**Design impact:** The design derives the unresolved and the resolved parent
from one source expression in `new()`, with `projects_dirs()` unedited, and
AC2's `PROJECTS_DIR` and default `~/projects` rows guard drift.

### N7. The working directory in PARENT
**Raised by:** adversary-engineer
**Concern:** With a relative `--into` or `PROJECTS_DIR`, "as given" takes the
physical working directory: `Path.absolute()` joins `os.getcwd()`, so from a
linked working directory the line names `ROOT/f/loop`, not
`ROOT/CWDLINK/loop` (council cases K and L, on all seven interpreters).
**Design impact:** The spec says PARENT is the parent as given, with `~`
expanded and made absolute against the working directory as the system
reports it (`os.getcwd()`, not `$PWD`); a test run from a linked working
directory expects the physical prefix.

### N8. (L) by its read
**Raised by:** adversary-engineer
**Concern:** (L)'s definition ("it, or a symbolic link on its path, loops") is
wider than its read: `LOOP/..` has a looping link on its path and is planned
into its directory on every version, base and patched (case A), while
`LOOP/sub/..` is (L) (case N).
**Design impact:** The spec defines (L) by the read: the parent's non-strict
`resolve()` raises `RuntimeError`, or `os.stat()` of the resolved parent fails
with `ELOOP`. `LOOP/..` keeps its answer and needs no scenario.

### N9. The `RuntimeError` mapping's reach
**Raised by:** adversary-engineer
**Concern:** `--into ~nosuchuser_x9/x` ends in `RuntimeError: Could not
determine home directory.`, exit 1, base and patched, on all seven
interpreters (case H), raised by `expanduser()` on the same line as S1. A
mapping that caught every `RuntimeError` around the parent expression would
print it as `ELOOP`.
**Design impact:** The `RuntimeError` mapping covers `resolve()` only, never
`expanduser()` or `Path.home()` (for example by expanding before the `try`,
as the feasibility copy does). Out of Scope names the unknown-`~user`
traceback as a residual.

### N10. The permission rows' skip probe
**Raised by:** adversary-engineer
**Concern:** For the row "a parent of mode 000" the destination does not
exist, so a probe that lstats the destination gets `ENOENT` as root, not
success, and the row would run and expect `EACCES`. As uid 1000 every probe
reads `EACCES` (an existing child, the absent destination and a path below the
child, under modes 000 and 600, on 3.10.21, 3.12.3 and 3.14.7), so the
probe's target matters only under root, capabilities or ACLs. The root case
was not run: this council's container refuses user namespaces.
**Design impact:** For every permission row, `setUp` creates a child of the
locked directory before the chmod, and the skip probe lstats that existing
child; the row is skipped only when that succeeds. AC3's "no (U) test is
skipped on any CI job" stands.

### N11. `import errno` is shared with feature 004
**Raised by:** systems-architect
**Concern:** Feature 004's realization adds `import errno` to `project`'s
import block (`004-project-clean-all-safe` at `66d60b6`), the import S1 and
S2 need, and "Ordering and shared files" does not name `project`. A three-way
merge of the feasibility copy with feature 004's `project` over `961c405` is
clean and keeps one `import errno`.
**Design impact:** The design names `project`'s import block as shared with
feature 004. The realization adds `import errno` only if main does not already
have it, keeps the block's order, and whichever lands second merges main in.

### N12. macOS runs the tool, but no CI job proves it
**Raised by:** adversary-engineer
**Concern:** Since #32 (Brett Heap, 2026-10-15) CI covers Linux only. The tool
still runs on macOS, where (L) and (U) print macOS's numbers and texts
(`ELOOP` 62, `ENAMETOOLONG` 63), a temporary directory resolves under
`/private/var`, and APFS has its own limits; the probe, the feasibility runs,
the council and CI ran Linux only.
**Design impact:** The tests build every expected line from `errno` and
`os.strerror()`, size names from `os.pathconf()`, and take paths under the
resolved base (`tests/test_project.py:117-120`), so they stay correct if run
on macOS. The spec claims versions, never systems; the README says CI covers
Linux, never macOS; and Risks names macOS as untested by CI. Re-adding a macOS
job is outside this change (#32).
