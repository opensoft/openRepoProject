## Council-Identified Constraints

### N1. The runner's loop mechanics
**Raised by:** systems-architect (SA-2, MEDIUM-HIGH; its requirement-level
parts are in `proposal.md`, What Changes, evidence model)
**Concern:** The proposal fixes the runner's outcomes: a probe `project`
stops at its record bound is complete, never `probe-failed`; after SIGKILL
the reap waits at most the 2 s grace, then abandons the child as
`probe-timeout`; every exit path terminates the process groups it started;
stderr is drained and capped. It leaves out the loop that delivers them, and
the obvious loops break them:
- stderr piped but read only after stdout: a chatty Git (a warning per
  worktree) fills the 64 KiB pipe, blocks on write until its budget expires,
  and the row becomes a false `probe-timeout`;
- under PEP 475 `select()` is retried after a handler that only sets a flag,
  so the apply-phase SIGINT flag (BA:463-464), and the SIGTERM and SIGHUP
  flags of OQ-16, are seen only when the select times out;
- `start_new_session=True` (C4) removes the cleanup a terminal gave the
  baseline: Ctrl-C and SIGHUP no longer reach Git children, so a path that
  unwinds without the runner's cleanup (`KeyboardInterrupt` before the apply
  phase, an exception inside the loop) leaves them running.
**Design impact:** design.md fixes the loop:
- stderr is drained in the same selector loop as stdout and capped, or sent
  to a temporary file; it never waits behind stdout;
- the selector timeout is a poll tick of 100 ms or less, shortened further
  to the nearest child budget or deadline;
- signal handlers only record the first signal received (it sets the exit
  status, OQ-16) and wake the loop, through `signal.set_wakeup_fd` or a
  self-pipe;
- `os.killpg` of every probe child's group runs in a `finally` clause on
  every exit path, `BaseException` included. A removal child in flight is
  outside that set ("A started removal is never interrupted", Rules This
  Change Keeps): the `finally` waits for it, and only the 300 s ceiling kills
  its group.
The fake `git`s of `proposal.md` Impact (one flooding stderr, one ignoring
SIGTERM, one printing 5,000 `!!` records) run through this loop. SIGTERM
during a planning probe of the SIGTERM-ignoring fake expects exit 143, zero
mutation, and `os.killpg(pgid, 0)` raising `ProcessLookupError` for its
group after the reap. The residual is recorded, not designed away: SIGKILL of
`project` itself runs no `finally`, so its probe children run on untimed and
a removal child runs to its own end; N4 covers what the latter can leave.

### N2. The runner is a child handle the overview can multiplex
**Raised by:** systems-architect of `add-project-overview`'s council (its
SA-2, MEDIUM-HIGH), routed to this change as cross-change item X1
**Concern:** Feature 004 ships the bounded runner for a strictly serial
`clean` (BA:427-458), and through `snapshot` its API is fixed at once by
`clean`, `status`, `doctor` and `update`. A blocking `run_bounded(argv) ->
result` call cannot run four children inside one event loop, so the
overview's feature 005 would either fork the runner, leaving two termination
paths and two environment scrubs, or refactor code this change owns.
**Design impact:** design.md shapes the runner as:
- a child handle: start (the caller's argv in its own process group, under
  the scrubbed environment), its readable stdout and stderr fds,
  `terminate_group()` (TERM, the 2 s grace, then KILL) and `reap()`, bounded
  as N1 states;
- a one-wide driver of that handle (N1's loop with one child), the serial
  path every `clean`, `status`, `doctor` and `update` call uses;
- the status, registry (`worktree list --porcelain -z`) and ref
  (`for-each-ref`) parsers as pure incremental byte parsers: fed chunks,
  doing no I/O, and reporting when a record bound is reached so that the
  driver stops the child with the complete-at-bound outcome.
`proposal.md` Impact carries the one sentence; `add-project-overview` drives
four handles from its own loop (its `clarifications.md`, N1). A test feeds
each parser a recorded stream one byte at a time and whole, and expects the
same records and the same bound either way.

### N3. An `in-use` gate, as a design option
**Raised by:** adversary-engineer (AE-2, HIGH; its gate is in `proposal.md`
as `unstarted-branch`)
**Concern:** "The current worktree is never removed" protects only the
process running `project` (`project-clean-review-safety/spec.md:9-13`).
Another session's working directory, an agent's or an editor's, is not
protected. `unstarted-branch` keeps a freshly created and published worktree
out (fixture `z`: `worktree add -b`, then `push -u`, no commit, read
`merged-removable` by the baseline), but a started worktree whose branch has
merged can still hold a live session when `--all-safe --apply --yes` runs;
that session then writes into a vanished tree. No commit is lost; work not
yet written is.
**Design impact:** Not an MVP requirement. design.md decides whether to offer
an `in-use` gate on Linux, excluding a row when any `/proc/<pid>/cwd`
resolves to its path or below it. If adopted, design.md states its place in
the gate order; one `/proc` scan per run, counted under the deadline; how an
unreadable entry (another user's process) is treated, failing closed or
recorded as best effort; and that macOS, with no `/proc`, and processes
outside the Linux instance (a Windows-side editor under WSL2) are not seen.
Adopting it adds a gate to the spec delta, so it returns to Brett Heap with
that delta; declining it records the reason and the residual in design.md.

### N4. Detecting a probable partial removal
**Raised by:** adversary-engineer (AE-1, HIGH; the never-signalled removal,
the ceiling and the note are in `proposal.md`)
**Concern:** A removal stopped after Git's own check passed leaves a
registered worktree with part of its tracked files deleted. In fixture `k`
(20,000 tracked files), TERM to the group after 0.25 s left 18,333 files,
the `.git` file and the registry entry, with Git exiting 143; the baseline
report then read the row `dirty`, "Preserve or commit the working changes
before cleanup." (`project:427-429`), and every later non-force removal
refused with 128. Under this change the child is never signalled before the
300 s ceiling, but the ceiling and a SIGKILL of `project` itself still leave
this state. If Git deleted `<path>/.git` before it stopped (readdir order
decides; a reading, not timed), the row fails the registration check and
reads `registration-mismatch`, an `inspection-error`, instead.
**Design impact:** design.md states how the report detects a probable
partial removal from evidence it already holds: a `dirty` row whose status
records are only deletions of tracked files (` D` in the `--porcelain=v1`
stream), with the `.git` file and the registry entry present. It also
states:
- how a stream stopped at its 4,097-record bound counts, the evidence then
  being a prefix (the note says "probable" either way);
- that the note is advisory: it never changes the classification, the
  ladder's names or order (OQ-28) or eligibility, and it is shown beside the
  `dirty` advice, never instead of it, with the recovery text "inspect, then
  `git worktree remove --force <path>` by hand";
- that the `registration-mismatch` case carries no partial-removal note, only
  the named manual remedy every plan-blocking refusal now has (What Changes,
  single-target).
The `proposal.md` scenario (SIGKILL of `project` and its child mid-deletion,
then a report) is the test, run once with fewer deletions than the record
bound and once with more.

### N5. The OQ-4 measurement protocol
**Raised by:** systems-architect (SA-3, MEDIUM; the 15 s budget outside a
deadline is in `proposal.md`, Decisions); the product advocate's survey
(PA-1) and the adversary engineer's deletion timing (AE-1) add to it
**Concern:** The cap arithmetic (BA:723-735) treats every Git child as a
constant 100 to 150 ms, but `git status` grows with index size and
`for-each-ref` with `%(upstream:track)` grows with branch count. A cold
cache, a large monorepo or a worktree on drvfs can pass the 5 s per-child
budget under `clean`'s deadline, and one failed `for-each-ref` leaves every
row's classification null (BA:625-627), so every plan is incomplete.
Fixture `k`'s 20,000-file removal took 1.27 s on overlay/ext4, and deletion
on drvfs is commonly ten or more times slower.
**Design impact:** The OpenSpec `tasks.md` carries one governance task, done
before the Speckit handoff, that records:
- the combined status probe timed against indexes of about 10,000 and
  100,000 entries, and `for-each-ref` in the shared format against about
  1,000 branches;
- each timed cold and warm, with the method used to get a cold cache
  recorded beside the numbers;
- a large removal (fixture `k`'s size) against the 5 s removal floor and the
  300 s ceiling;
- the fit test of BA:729-735 reapplied with the measured costs, on this
  workstation (Git 2.43, WSL2) and a Linux filesystem path;
- drvfs measured the same way and recorded as a stated degraded case, never
  used for the fit;
- each surveyed repository's eligible-row count beside the timing (PA-1's
  survey found about 20 such rows in Opensoft-Tenant).
Until the task is done the spec deltas mark the caps provisional (Decisions,
OQ-4).
