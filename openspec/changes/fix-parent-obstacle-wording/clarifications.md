## Council-Identified Constraints

### N1. The parent read differs by Python version
**Raised by:** systems-architect (adversary-engineer raised the same, N5)
**Concern:** The two parent cases are told apart by pathlib's `is_dir()` and
`exists()` on the resolved parent, and what reaches them depends on the
interpreter. On Python 3.10 and 3.12, the CI matrix, the read was verified: a
missing parent and a dangling symbolic link read as not existing, a regular
file, a symbolic link to one and a FIFO read as existing and not a directory,
a symbolic-link loop raises `RuntimeError` at `resolve()` (`project:315`)
before the question, and a parent beneath a directory without search
permission raises `PermissionError` at `destination.exists()` (`project:321`)
before the question. On Python 3.13 and later a symbolic-link loop no longer
raises at `resolve()`, so it reaches the read and prints today's
missing-parent sentence. On 3.14 an existing directory under an unsearchable
ancestor is no longer refused at `destination.exists()`, and it too prints the
missing-parent sentence.
**Design impact:** The design states the versions the read was verified on
(3.10 and 3.12) and records the two later-version outcomes as residuals: both
are the pre-existing wording, on versions CI does not run, unchanged by this
change. The discriminator does not add `is_symlink()`: a loop is not one of
the two cases. CI additions are not this change's.

### N2. Fixtures, expected paths and rows for the new tests
**Raised by:** systems-architect
**Concern:** A parent that exists and is not a directory needs fixtures the
tests create, and its expected PARENT must be the path `new()` resolves (on
macOS a temporary directory under `/var` resolves to `/private/var`). The
existing "nothing created" assertion, `(parent / name).exists()`, is vacuous
beneath a file, since nothing can exist there. The routes test
(`test_pty_missing_parent_is_named_without_into`) and the dry-run test
(`test_pty_dry_run_with_an_obstacle_refuses`) build their own cases and do not
read `known_obstacle_cases()`, so rows added there reach neither. A fixture
added inside the D13 block would stop it being a verbatim copy of the archived
design.
**Design impact:** `known_obstacle_cases()` creates its own file and symbolic
link fixtures and returns `self.base / "<file>"`, the resolved path, as the
expected PARENT for both the file row and the symbolic-link-to-file row. For
the non-directory rows, the tests assert that nothing was created with the
dry-run test's `sorted(self.base.rglob("*"))` snapshot, plus the file's type
and content unchanged. The routes test and the dry-run test gain explicit
rows. The new fixture goes after the `# End D13 fixtures.` marker, under its
own header naming this change's design.

### N3. How the two parent cases are told apart
**Raised by:** systems-architect
**Concern:** Which sentence is printed could be read as `parent.exists()` or
as a raw `os.stat` of the parent. The question line and the composed refusal
must name the same sentence.
**Design impact:** The design chooses `exists()` over a raw stat: it has the
same error handling as `is_dir()` on every version, so the second read adds no
exception path the first does not have. The obstacles are computed once, as
today (`project:332`), and that one list feeds both the question
(`print_creation_question()`) and the refusal (`project:338-339`), so the two
cannot diverge.

### N4. The ASCII check covers the changed text, not the whole file
**Raised by:** systems-architect
**Concern:** `project` already carries em dashes, in report strings this
change does not touch, at lines 197, 908, 921 and 1129 at `7a9134b` (the
council's note cited 197, 912 and 925; re-counted with
`grep -nP '[^\x00-\x7F]' project`). A whole-file ASCII check fails before and
after this change.
**Design impact:** The ASCII check in the tasks of the realization covers the
changed strings and the added lines of `project`, `tests/test_project.py` and
`README.md`, not the whole of `project`. The existing em dashes are not this
change's to replace.

### N5. The read stays pathlib (the lead's decision)
**Raised by:** adversary-engineer
**Concern:** The outcome for a looping or unreadable parent depends on the
Python version (N1), while the README requires "Python 3.10+" and CI runs
3.10 and 3.12 only. A raw `os.stat` classified by errno, and a change to the
CI matrix, were weighed.
**Design impact:** The lead decided: the read stays pathlib `is_dir()` then
`exists()`, which share their error handling on every version. A raw
`os.stat` classified by errno is rejected for this change: it would add
behaviour, strings and a third case beyond the wording follow-up. The 3.13
and later symbolic-link loop and the 3.14 unsearchable ancestor are recorded
as residuals on versions CI does not run. Changing the CI matrix or the
README's "3.10+" is not this change's.

### N6. Assumptions the adversary confirmed
**Raised by:** adversary-engineer
**Concern:** None open. The adversary confirmed these assumptions of the
proposal: `resolve()` at `project:315` runs for every parent source
(`--into`, the positional parent, `PROJECTS_DIR`, `~/projects`); the question
and the refusal print from the same obstacles list, computed once; a FIFO
parent gets the new sentence; a trailing slash is normalised; on macOS the
letter case of the path is kept as typed; a second parent sentence is a line
inside the existing question, not a new surface or form (the archived
change's N4 and N5 are untouched); the obstacle read before the question is
reused in the refusal, so a parent repaired in another terminal while the
question waits is refused with the old sentence until a rerun (pre-existing,
low); a writability check would be a fourth read, outside scope; and, for
security, the resolved path reveals no more than `readlink` shows.
**Design impact:** The design relies on these as stated and adds nothing for
them: no re-read at the refusal, no writability read, no new surface.
