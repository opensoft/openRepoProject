## Council-Identified Constraints

### N1. The scheduler's control loop
**Raised by:** systems-architect (SA-1, HIGH)
**Concern:** The proposal names the parts, a four-way scheduler with an
in-flight child registry and daemon filesystem workers (Impact; requirements
3 and 11), but not the loop that drives them, and each obvious design in a
single-file Python program breaks a stated bound:
- a main thread blocked on one wait (a 5 s filesystem task, or one child's
  stream) neither reads nor times the other children; their pipes fill at
  64 KiB, `git status` blocks on write, and the 5 s and 60 s bounds stop
  holding;
- a SIGTERM or SIGHUP handler that raises an `Exception` subclass is caught
  by the per-candidate collector, which catches `Exception` (DI:534), and
  becomes an `internal-error` row, so the run continues;
- a handler that walks the registry between `Popen()` and registration
  misses that child, which then outlives `project` under
  `start_new_session=True`;
- standard error is kept only to 200 characters (DI:544-545) but must be
  drained the whole time, or it blocks the child the same way.
**Design impact:** design.md fixes the loop:
- one main-thread `selectors` loop over every child's stdout and stderr;
  filesystem workers post completions to a queue plus a self-pipe the loop
  watches; each selector timeout is the nearest of the child budgets, the
  task waits and the deadline;
- signal handlers only record the first signal and wake the loop through
  `signal.set_wakeup_fd`, or raise a `BaseException` subclass; termination
  runs in one `finally`;
- each child is spawned and registered under
  `signal.pthread_sigmask(SIG_BLOCK)`; stderr is drained continuously and
  its first 200 characters kept.
A test runs one hung child and one large-output child at concurrency 4,
then sends SIGTERM, and expects exit 143, no result document, and
`os.killpg(pgid, 0)` raising `ProcessLookupError` for every child's group.
The residual is recorded, not designed away: SIGKILL of `project` itself
can orphan read-only children, which then run untimed.

### N2. Abandoned listing workers stop competing
**Raised by:** systems-architect (SA-4, MEDIUM; its bounds part is V8 in
`proposal.md`)
**Concern:** A root cut at its 5 s listing bound is usually slow, not
stuck. Its daemon thread keeps calling `scandir` across up to 4,096 entry
directories after the overview has moved on (DI:469-485), competing for I/O
and the GIL with the timed Git phase.
**Design impact:** Each listing worker checks a cancel flag between entries
and stops once its root is abandoned, by its 5 s bound or by the deadline. A
call already stuck in the kernel stays abandoned, as DI:480-485 allows. A
test with an injected slow `scandir` asserts that no entry is read after
the root is cut.

### N3. Deriving `repository.root` for gitfile checkouts and missing main worktrees
**Raised by:** adversary-engineer (AE-2, MEDIUM-HIGH); the systems
architect's identity review is the cross-examined view
**Concern:** Requirement 2 fixes the outcomes (V2): a first registry record
whose path equals `common_dir` marks a gitfile main checkout, whose
`repository.root` is the realpath of `core.worktree`, else the
`--show-toplevel` of a candidate that is that checkout, else null with
`unsupported-layout`; a missing main worktree gives a null root with
`main-worktree-missing` and runs the repository-wide probes in the
candidate. How each is derived is design. The fixtures show the cases
differ:
- `git init --separate-git-dir`: the first registry record is the git
  directory, not the checkout; `git -C <git directory> status` fails with
  "this operation must be run in a work tree" (exit 128); and the git
  directory has no `core.worktree` (`git config --get core.worktree` exits
  1), so only the candidate match can find the checkout;
- a submodule: the first record is `<superproject>/.git/modules/<name>`,
  and its `core.worktree` is relative (`../../../<name>`), to be resolved
  against the git directory as [E]'s registration rule resolves relative
  values (BA:230-232).
**Design impact:** design.md states:
- whether `core.worktree` is read by a counted, bounded Git child or from
  the identity probe's own output, and how `probes.estimated` counts it;
- which candidate "is that checkout": one whose identity probe reported
  this `common_dir` and whose `.git` file names `common_dir` itself, not
  `common_dir/worktrees/<id>`;
- whether the main worktree row then names `repository.root` and takes the
  status probe there, so the checkout's dirty state is reported (AE-2's
  hidden-dirty consequence), while the git-directory record is never
  status-probed;
- for a missing main worktree, how presence is established (the bounded
  `lstat` task), where the merge target's manifest is read when
  `repository.root` is null (DI:583-585 reads it there deliberately), and
  that no clean suggestion is emitted;
- that a submodule checkout's suggestion follows change 1's
  `Clean resolves its target Git-first` as ratified (cross-change item X2
  asks change 1 to refuse it with `target-not-repository-root`).
Tests cover `--separate-git-dir` with and without its checkout among the
candidates, a submodule entry under a root, and a main worktree deleted
while a linked worktree remains.

### N4. Computing the default-branch finding set
**Raised by:** adversary-engineer (AE-1, HIGH)
**Concern:** V1 replaces `acf0133`'s first-match chain with every
applicable finding on a `protected-default` checkout, adding `unpublished`
for no upstream and `remote-gone` for a gone upstream. For `refs/heads/*`,
`%(upstream:track,nobracket)` is empty with no upstream and `gone` once
the upstream is pruned (DI:349-351), and `ahead` and `behind` are then null
(DI:783). Re-run on Git 2.43.0: a `main` pushed with `git push origin main`
(no `-u`) and then given two commits lists `refs/heads/main` with an empty
`%(upstream)`, while `git rev-list --count origin/main..main` prints 2.
`acf0133` returns `ok` for that row (its `health_status`, line 37 of the
commit's diff).
**Design impact:** The set is computed from the row's `dirty`, `upstream`,
upstream track state, `ahead` and `behind`, all already in the overview's
evidence, in a fixed order with no new probe: `dirty` first; then at most
one of `unpublished` (no upstream), `remote-gone` (upstream gone),
`diverged`, `unpushed` or `remote-ahead`. A checkout whose status probe
failed is `inspection-error` under change 1's R1 and gets none of these.
The two new cases use the fixed message "merge-target branch has no
upstream; local commits are unverified" and the `remote-gone` message, both
with `suggested_command: null`. Findings are emitted in DI:755's order
(checkout path, then code), so the computation order never shows in output.
